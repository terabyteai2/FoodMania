  4. BACKEND — Configuration & JWT Token Shapes
================================================================================

Settings (backend/config.py) — pydantic.BaseSettings loaded from .env (~50 fields):
  DATABASE_URL, SECRET_KEY, BASE_URL, GOOGLE_CLIENT_IDS, MAPBOX_ACCESS_TOKEN,
  FIREBASE_PROJECT_ID, R2_ENDPOINT, R2_*, UDDOKTAPAY_API_KEY,
  PLATFORM_ADMIN_EMAIL, ONECODESOFT_API_KEY, TWILIO_*, GROQ_API_KEY,
  OPENAI_API_KEY, FACEBOOK_*, etc.

JWT token payloads (backend/auth.py):
  Device token:  { sub: outlet_id, account_id?, exp }  (365d)
  Platform token: { sub: admin_id, type: "platform", exp }  (8h)
  Signup token:  { type: "phone_signup", phone, purpose?, invite_id?, exp }  (15m)

Dict shapes:
  subscription_access_dict(): { hasAppAccess, subscriptionStatus, subscriptionPlan, subscriptionExpiresAt }
  subscription_to_dict():     { id, outletId, outletName, plan, status, startsAt, expiresAt, ... }
  blocking_notice:            { enabled, title, message, imageUrl, inputField, inputLabel, updatedAt }
  app_update:                 { enabled, versionName, versionCode, apkUrl, releaseNotes, required, publishedAt }
  push_notification payload:  { type, orderId, status, serialNumber, actionTarget }

Helper response shapes:
  ok(data)  -> { data, error: null }
  err(msg)  -> { error: msg }

================================================================================
  KEY DESIGN INVARIANTS (from spec + status_report)
================================================================================
- All money is integer-ish BDT Taka (Numeric fields in DB, double in Dart).
- NULL-safe DB additions: every new column defaults NULL = "not configured".
  Existing logic behaves exactly as before when null.
- No forced customer data for FOH (dine-in/parcel/counter) — customer identity
  comes only from online channels (Messenger, website).
- Bilingual EN+বাংলা throughout; name fields have separate _en/_bn columns.
- Tags encoded as simple strings in menu_item.tags_json (no separate ModGroup table);
  parsed client-side into MenuItemExtras.
- Order lifecycle: pending -> accepted -> completed; rejected removes from flow.
  Legacy states (preparing, ready, served, cancelled) normalize at read time.
- Printing dedup: kot_batches JSONB + PrinterService hasPrintedOrderId() set.
